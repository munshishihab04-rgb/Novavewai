# Jobs vertical — bounded implementation and deployment gate

## Outcome
Native `jobs_search` is wired into the real agent loop, not just a helper. The actual authenticated run machinery/receipts are exercised with a controlled provider and temporary PostgreSQL. City grounding runs server-side against user-role messages before source access, so a model-invented city cannot browse. Missing or ambiguous city asks first. Occupation/sector is inferred from a finite vocabulary, including cooking → cuoco; unsupported occupations ask what work the user wants. Optional preferences never become an interview prerequisite.

Subito is one adapter, not the discovery architecture. `src/jobs-discovery.ts` defines distinct opportunity kind, source host type, publisher type, evidence timestamps and verification status; it also contains a bounded provider-neutral progressive search → companies → verification → browser orchestrator. **That extension is fixture-tested but not wired to live company/search/official-domain providers. Full MVP-1 is NOT complete.** No company discovery or Careers verification is claimed available in the agent instructions.

Parent must establish permission/terms and current source access. Even after configuration, robots/access failures stop the adapter.

Real Playwright Chromium executed local DOM parser and UI tests. **No successful live Subito job retrieval is asserted.** Tests use clearly labelled controlled fixtures; fixtures are never a runtime fallback. Browser adapter is conservative server-rendered HTML only (`javaScriptEnabled:false`); real DOM selectors, geographic URLs and completeness remain unverified on current Subito. Changed layout returns `jobs_parse_failed`, not fabricated/empty success. Search cards do not certify vacancy availability. Subito results remain UNVERIFIED, publisher UNKNOWN. Strict no-agencies excludes all such unknowns and reports the excluded count. The engine does not infer direct employment from Privato/Azienda verificata.

## Limits / data
- One browser per process plus an atomic shared-directory browser lock across API/warm processes. Lock is fail-closed after a crash; operator must verify no browser/warm/API search is active before removing a stale `browser.lock`. Do not run processes with different cache roots.
- Source: one robots document + one city/role search document, at most three request attempts, exact HTTPS origin/URL allowlist, no scripts/images/downloads/service workers, no detail/contacts pages, no pagination, no cookies/profile/login. 7s launch, 10s navigation, 25s browser deadline; native tool cancellation/timeout race at 30s.
- At most 8 deduped compact jobs per search, 120-character title, no description/photos/contact fields. Original links only. Optional structured time metadata; no salary-period normalization or employer certification. Phone/email-looking title strings are redacted.
- Shared cache: hashed canonical role/city only, no user identity/query/CV/preferences. Six-hour TTL (bounded configurable constructor), explicit fetchedAt/expiresAt, no stale fallback on source error. Twelve supported city mappings, thirteen canonical role/sector choices bound key cardinality. Strict preferences are applied after cache retrieval.
- Live misses: 15s minimum interval; 40 attempts per UTC day, shared durable budget. Warm cache reserves once per UTC day, max five cities (Bologna/Milano/Roma/Napoli/Torino), one sector (ristorazione), max 180s, stops on source failure. No mass city×sector grid or radar.
- Progressive extension: max four stages, 30s overall, at most 30 candidates/provider and 12 output candidates, up to six verification candidates; exact source-URL+kind dedupe only. Semantic cross-source matching/official-source preference are still gaps, not silently claimed implemented.
- UI renders escaped receipt titles, unverified status, timestamps and an `Apri annuncio originale` anchor with `noopener noreferrer`. No contacts. Existing personal welcome copy is unchanged. Current receipt cards reopen from the latest run; historical job-card history across later runs is not yet a separate persisted view.
